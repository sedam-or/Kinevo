# WORKFLOW.md: how a task is done

Applies to every implementer, human or agent. Rules of precedence and the non-negotiables are in [`AGENTS.md`](AGENTS.md). The task template is [`tasks/_template.md`](tasks/_template.md).

## 1. Task status lifecycle

```
draft ──► todo ──► in_progress ──► review ──► done
                     │    ▲           │
                     ▼    │           ▼
                   blocked │    changes_requested
                     │     │           │
                     └► todo           └──────► in_progress
```

| Transition | Who | When |
|---|---|---|
| `draft → todo` | architect | the milestone before has its integration task `done`, and the task passed the consistency gate |
| `todo → in_progress` | implementer | Step 0 below; every dependency is `done` |
| `in_progress → blocked` | implementer | the blocking procedure (§3) applies |
| `blocked → todo` | architect | a `Resolved (architect, YYYY-MM-DD)` line answers every open question; spec and neighbouring tasks are fixed in the same commit |
| `in_progress → review` | implementer | Steps 1–10 are complete and `just check` passes |
| `review → changes_requested` | reviewer | the review found a defect against the task, spec or DoD |
| `changes_requested → in_progress` | implementer | work on the review comments starts |
| `review → done` | maintainer | the PR is merged (squash); the maintainer sets `done` in the merge commit or right after it |

The status lives in the task file's front matter (`status:`). `tasks/index.md` is regenerated by `python3 scripts/tasks_index.py` and must never be edited by hand.

## 2. The steps

**Step 0: pick and claim.** Take the lowest-numbered task with `status: todo` whose `depends_on` are all `done`. Set `status: in_progress` and `assignee:`. Commit (`docs(tasks): start T-nnn [T-nnn]`) on the task branch (step 3) and push it, so nobody else takes the task.

1. **Read.** Read the whole task. Open every spec section it cites. The inlined excerpts are copies: if an excerpt differs from the spec, the spec wins and you block. Read the files listed under *Files* that already exist.
2. **Check preconditions.** Dependencies are merged on `main` (or, in a maintainer-authorised stacked run, satisfied as defined in `BRANCHING.md` §6); files the task says exist do exist, and files it creates do not; the commands under *Tests* run in your environment. Any failure here is a block, not a workaround.
3. **Branch.** Create the branch named in the task (`BRANCHING.md` §2) from up-to-date `main`.
4. **Write the tests first.** Turn every *Acceptance* criterion (Given/When/Then) into the test named next to it. Run them and see them fail for the expected reason.
5. **Implement the minimum.** Make the tests pass, touching only the files under *Files*. Follow *Interfaces*, *Business rules*, *Security* and *Implementation notes* literally. No extra features, no speculative abstractions, no drive-by refactors (`CLAUDE.md` §2–3).
6. **Run the full gate.** `just check` (before M1 exists: the scripts listed in `AGENTS.md`). Everything must pass. Never weaken, skip or delete a test to get there.
7. **Self-review.** Walk the *Definition of done* line by line, then the task's *Security* section, then CQ and CA (`spec/standards/code-quality.md`, `clean-architecture.md`). Check the diff size against the task budget (about 400 changed lines). If it is over 1.5× the budget, block (§3) instead of shipping.
8. **Regenerate contracts the task names.** Only those: OpenAPI document, `cargo sqlx prepare` metadata, i18n catalogues, `tasks/index.md`. Commit the regenerated files.
9. **Write the Report** in the task file (§4).
10. **Request review.** Set `status: review`. Commit following `COMMIT_CONVENTION.md` with `[T-nnn]` in the subject, signed off (`git commit -s`).
11. **Open the PR.** Push and open a PR with the PR template. The title is the squash-commit subject. The body links the task and pastes the Report's *Commands run* block.
12. **Respond to review.** On `changes_requested`, set `in_progress`, fix with new commits (no force-push), re-run step 6, update the Report and set `review` again. Never merge your own PR.

## 3. Blocking procedure

**Block when any of these is true:**

- the task and the spec disagree, or two spec files disagree;
- a value the work needs is missing (a business value is a question, never a guess);
- the work needs a file that is not listed under *Files*, or a change outside *Scope In*;
- an acceptance criterion cannot be satisfied as written, or cannot be tested;
- a precondition from step 2 fails and fixing it is outside the task;
- the diff would exceed 1.5× the line budget;
- a dependency, licence or security concern is not covered by the spec.

**Then:**

1. Stop changing code. Keep whatever work exists on the branch; do not delete it.
2. In the task's *Questions* section, add one entry per issue:
   ```
   - Q-n (implementer, YYYY-MM-DD): <what is wrong, with file:line or spec id>
     Options: (a) … (b) …
     Recommendation: (a) because …
   ```
3. Set `status: blocked`. Commit (`docs(tasks): block T-nnn: <short reason> [T-nnn]`), push, and comment on the task's issue or PR with a link to the question.
4. Do not start another task that depends on this one. You may pick an unrelated `todo` task.

The architect answers each question with `Resolved (architect, YYYY-MM-DD): …` under it. The same commit fixes the spec and every affected task, and re-runs the consistency checks. Then the task returns to `todo`.

## 4. Report structure

Every task file ends with a filled-in *Report* section, in this order:

1. **Summary.** Two or three sentences: what now works.
2. **Acceptance results.** Table: criterion id → test name → result (`pass` / `fail` / `not run`, with a reason for anything other than `pass`).
3. **Commands run.** The exact commands, each with its exit code, plus the last lines of output for anything that failed or was skipped.
4. **Files changed.** Path → lines added/removed (from `git diff --stat main...HEAD`).
5. **Deviations.** Anything done differently from the task, with the reason. Write "none" if there were none.
6. **Spec issues noticed.** Problems that did not block this task but will affect others.
7. **Not done / not verified.** Everything that was skipped or could not be checked. Never leave this out: "nothing" is a valid answer only if it is true.
8. **Follow-up suggestions.** Optional. Ideas that are out of scope, for the architect to decide on.
