# T-454: Add the 1-click deploy templates, their lint and smoke scripts, and the cloud operator checklist

## Goal

Each supported hosting platform has a template that deploys the same image with generated secrets, a script proves the templates are consistent with the application's environment, and the cloud checklist is machine-checkable where possible.

## Context

> **Channels** (`spec/14-distribution.md` §1): 1-click templates for Railway, Render, Fly.io, Coolify and Cloudron `[ASSUMED priorities]`, kept in `deploy/<provider>/` and tested by a smoke script. **DST-04** each template pre-fills only non-secret defaults and generates secrets via the platform's secret mechanism; each lists the exact environment variables and the post-deploy URL. **DST-01** one image serves all channels; differences are configuration only. **DST-08** `cosign verify` and checksum commands are documented (docs live in Phase 5; this task provides the verification script `scripts/verify-image.sh`).
> **Environment truth** (T-039/T-040/T-056 define it): `KINEVO_DATABASE_URL` family (three role URLs) or the bootstrap URL (D-50), `KINEVO_SECRET_KEY`, `KINEVO_PUBLIC_URL`, optional TLS files, setup variables. The template lint reads `crates/kinevo-app` config definitions (exported by `kinevo config schema`, a subcommand added here as a thin read-only listing of environment variable names, whether required, and secret-ness; add to T-040's CLI module) and fails when a template references an unknown variable, omits a required one, or marks a secret variable as plain.
> **Smoke** (`scripts/deploy-smoke.sh <base_url>`): waits for `/readyz`, checks `/livez`, fetches `/api/v1/instance`, confirms the setup gate (`setup_required` on a protected route), and exits non-zero otherwise; used against the Compose stack in CI (DST-06) and by operators after a one-click deploy. Real provider deploy tests are manual and **environment-limited**; nothing here contacts a provider.
> **Cloud checklist** (`spec/15-cloud.md` CLD-01/04): `scripts/cloud-preflight.sh` checks on a running instance that the cloud template's modules are on, `auth.registration.mode=open`, billing is refused while `billing.currency`/`billing.plans` are unset (`billing_not_configured`), `/readyz` is healthy and security headers are present; it prints items that only the operator can verify (backups, restore drill, alerts, legal documents — M-LEGAL, M-INFRA) as `MANUAL`. No secrets are written anywhere.

## Scope

**In:**
- `deploy/{railway,render,fly,coolify,cloudron}/**` templates (formats per platform's public spec; each with README listing variables and URL), `kinevo config schema` subcommand, `scripts/{lint-deploy.py,deploy-smoke.sh,verify-image.sh,cloud-preflight.sh}`, tests for the lint and the scripts (bats-free: Python `unittest` or shell with a fake server), `just deploy-lint` recipe wired into `just spec`.

**Out:**
- Workflows and docs pages (Phase 5), real provider deploys.

## Interfaces

```text
$ kinevo config schema --format json     # [{ "name": "KINEVO_SECRET_KEY", "required": true, "secret": true, "file_variant": true }, …]
$ scripts/deploy-smoke.sh https://host   # exit 0 only when ready and gated
```

## Business rules

1. Templates never contain secret values; secrets are generated by the platform mechanism or left for the operator.
2. The lint is the source of truth for template/application agreement.
3. Scripts never print secrets.

## Security

- Scripts read secrets only from files or environment names passed by the operator; shellcheck-clean.
- Images are referenced by digest or version tag from the release process; the template lint rejects `latest` for stateful deployments.

## Implementation notes

- If a platform's template format cannot be validated offline, the lint checks structure only and the Report lists the platform as manual.
